# `themvora init`

## Prerequisites
- Node.js 18+
- Project with @themvora/cli installed or npx access

Create a project, or integrate Themvora into one you already have.

`init` has a different job from `generate`. `generate` turns a seed, preset or
brand into theme data and writes a file. `init` works on a *project*:

```text
project directory
        ↓
detect or choose framework
        ↓
choose a theme source
        ↓
scaffold (a new project) or integrate (an existing one)
        ↓
install the Themvora packages
        ↓
wire the provider, passing the theme registry as props
        ↓
verify by running the project's own build and typecheck
```

The goal is not to write a configuration file. The goal is:

> **Run `themvora init …` and end with an actually working, minimally themed
> application.**

## Interactive project creation

Run `themvora init` with no directory, in a terminal, and the CLI opens a guided
wizard:

```text
? What would you like to name your project? my-app
? Which package manager would you like to use? pnpm
? Which framework would you like to use? React
? Would you like to use Tailwind CSS with Themvora? No — Plain CSS
```

Four questions, in that order:

| Question | Asked when |
| -------- | ---------- |
| Project name | No directory was given, and the current directory is not already a project |
| Package manager | `--tool` was not supplied, and nothing in the target identifies one |
| Framework | `--framework` was not supplied, and the target is a new project |
| Tailwind or plain CSS | `--styling` was not supplied, and the target is a new project |

The last question has **No — Plain CSS** preselected — the same value a run
without a terminal uses. *Yes — Tailwind CSS* installs the Tailwind integration
instead.

Explicit flags win, and nothing already supplied is asked for again:

| Command | What it asks |
| ------- | ------------ |
| `themvora init` | name, package manager, framework, styling |
| `themvora init my-app` | package manager, framework, styling |
| `themvora init my-app --tool pnpm` | framework, styling |
| `themvora init my-app --framework react` | package manager, styling |
| `themvora init my-app --tool pnpm --framework react` | styling |
| `themvora init my-app --tool pnpm --framework react --styling css` | nothing |

Once the answers are in, the wizard hands over to the normal pipeline: it
validates the configuration, scaffolds the framework with its official
generator, integrates Themvora, installs the dependencies once, runs the
project's own build and typecheck, and prints the command that starts the app.

```bash
# Interactive project creation
themvora init

# Explicit project configuration
themvora init my-app --tool pnpm --framework react

# Next.js with npm
themvora init my-app --tool npm --framework next

# Vue with bun
themvora init my-app --tool bun --framework vue

# Backward-compatible package-manager option
themvora init my-app --package-manager pnpm --framework react
```

`themvora init .` is never a name question: a directory was named, so it is
scaffolded in place.

### Cancelling

Ctrl+C at any question exits `130` and writes nothing. The questions run before
a plan exists, so there is no half-scaffolded directory to clean up — and that
includes the styling question, which is asked before a single file is written.

### When the wizard does not run

There is no wizard without a terminal. `--json`, `--quiet`, `--plan`,
`--dry-run`, `CI`, `TERM=dumb`, and a redirected stdin all keep `init`
non-interactive — and a missing value then becomes a usage error that names the
flag supplying it:

```text
$ themvora init my-app --json
Usage: themvora init [dir] [options]
a new project needs --framework <id> (supported: react, next, vue, svelte, solid)
```

## Package managers

`--tool` selects the package manager that drives the framework's generator and
performs the dependency install:

```bash
themvora init my-app --tool pnpm --framework react
themvora init my-app --tool bun --framework vue
```

| Value | Scaffolder invocation | Install |
| ----- | --------------------- | ------- |
| `npm` | `npm create vite@latest …` · `npx --yes create-next-app@latest …` | `npm install` |
| `pnpm` | `pnpm create vite@latest …` · `pnpm dlx create-next-app@latest …` | `pnpm add` |
| `yarn` | `yarn create vite@latest …` · `yarn dlx create-next-app@latest …` | `yarn add` |
| `bun` | `bun create vite …` · `bunx create-next-app@latest …` | `bun add` |

`--package-manager <name>` is the same option under its earlier spelling. Both
resolve to one internal value; supplying both with **different** values is an
argument conflict rather than a silent choice:

```text
$ themvora init my-app --tool pnpm --package-manager yarn --framework react
Usage: themvora init [dir] [options]
--tool and --package-manager disagree (--tool pnpm and --package-manager yarn) — pass a single package manager
```

When neither flag is given, detection decides, in this order:

1. the corepack `packageManager` field, because it is an explicit declaration;
2. the first lockfile found;
3. `npm`, when there is neither.

Several lockfiles are reported as a warning rather than silently resolved. A
manager you named explicitly is checked before anything runs: if `pnpm` is not
on `PATH`, `init` stops with an actionable error instead of quietly installing
with npm.

The wizard's menu preselects the manager that invoked the CLI, so `pnpm init`
lands on pnpm. That is a default in a prompt, not a fourth detection rule: a
non-interactive run has nobody to suggest it to, and falls back to npm.

## Supported frameworks

```bash
themvora init my-app --framework react
themvora init my-app --framework next
themvora init my-app --framework vue
themvora init my-app --framework svelte
themvora init my-app --framework solid
```

`init` currently scaffolds and integrates **React + Vite, Next.js App Router,
Vue 3 + Vite, Svelte 5 + Vite, and Solid + Vite**. Themvora may support
additional frameworks at the package level — Angular, Nuxt, Astro and Remix are
fully supported by their own packages and documented — but that does **not** mean
the CLI scaffolder supports every one of them yet.

| Framework | Target | Build system | Rendering |
| --------- | ------ | ------------ | --------- |
| React | React + Vite | Vite | Client |
| Next.js | App Router | Next | Server |
| Vue | Vue 3 + Vite | Vite | Client |
| Svelte | Svelte 5 + Vite | Vite | Client |
| Solid | Solid + Vite | Vite | Client |

`themvora list frameworks` prints the same set, from the same registry. Asking for
a published-but-unsupported framework says so explicitly rather than reporting an
unknown name:

```bash
themvora init my-app --framework nuxt
# "nuxt" is a supported Themvora integration but is not an `init` target yet
# — init supports: react, next, vue, svelte, solid
```

## A new project

```bash
themvora init my-app --framework react
```

The project is created with the framework's **own** generator — `create-vite` or
`create-next-app` — and Themvora then integrates into the result. Themvora does
not ship a copy of anyone's starter template, because such a copy is stale the
moment that framework changes its template.

After scaffolding, the integration is computed from the generator's real output
rather than from an assumption about it, and the project is verified by running
its own `build` and `typecheck` scripts.

### Installation happens once, and it is Themvora's

The generators can install dependencies themselves, and every one of them asks
first — `create-vite` with *"Install with npm and start now?"*. That question is
suppressed, because for a Themvora starter either answer is wrong: the CLI
installs the framework packages regardless, so answering *No* still ends in an
install and answering *Yes* installs the tree twice.

`init` therefore passes each generator its own documented non-interactive flag —
`--no-interactive` for `create-vite`, `--skip-install` for `create-next-app` —
and runs **one** install itself, after the integration has finished editing
`package.json`:

```text
scaffold (no install)
        ↓
integrate — write the theme module, the showcase, the provider props
        ↓
record build-time dependencies in package.json (Tailwind only)
        ↓
install once, with the selected package manager
        ↓
verify — the project's own build and typecheck
```

Tailwind's compiler and its plugin are `devDependencies`, and package managers
only take a dev flag for a whole command — so the obvious implementation is a
second `add -D` right after the first. That is two full resolutions of one
dependency tree for one new project, and it is not what happens here. The
integration writes those two entries into `package.json` first, which means the
single install already sees them and produces one lockfile entry set.

`--no-install` is still supported and still means "install nothing": it drops
Themvora's install step, and the generator's install is already suppressed. The
manifest is still written in full, so a `pnpm install` you run yourself produces
the same project. The dependency-backed verification steps are then reported as
**skipped** rather than failed, because a build that cannot resolve its
dependencies is not evidence that the generated code is broken.

The development server is never started automatically. `init` prints the command
that starts it, with the selected manager's own syntax:

```text
Project created successfully!

Next steps:

  cd /path/to/my-app
  pnpm run dev
```

## An existing project

```bash
themvora init . --framework react
```

The framework is detected from `package.json`; `--framework` overrides detection.

Two properties matter more than the features here:

- **Your files are not replaced.** A file that is wholly Themvora's — the theme
  module and the showcase components — is written only when it does not exist.
  If you already have one of your own, `init` stops and asks for `--force`. The
  application root is a special case: in a project Themvora scaffolded it is
  replaced, and in one you already had it is left alone entirely.
- **Running it twice does nothing the second time.** Re-running `init` on an
  integrated project reports `0 created · 0 updated` and leaves the tree
  byte-identical. That is asserted by the test suite, not assumed.

When a file is not in a shape `init` recognises — a root element it cannot match,
a `plugins` array written unusually — it does **not** guess. It reports the exact
snippet to add, under `manual steps`.

## Theme sources

| Flag | Result |
| ---- | ------ |
| _(none)_ | Core's built-in neutral `light` / `dark` pair |
| `--preset <id>` | A canonical preset from the catalog |
| `--brand <id>` | A brand-inspired recipe from the catalog |
| `--seed <color>` | A theme generated from the seed |

```bash
themvora init my-app --framework react --preset mint
themvora init my-app --framework react --brand apple
themvora init my-app --framework react --seed "#3366ff"
```

Presets and brands are read from the same catalog the docs pages render, so the
theme written into your project is byte-for-byte the theme the docs show. A seed
goes through `generateTheme`. The resolved theme is validated **before** anything
is written.

## The generated project

The generated application is the **Themvora showcase** — the same interactive
reference the docs site renders, not a placeholder:

```text
Themvora
Theming that survives contact with a real app

[Read the docs] [Next.js guide] [Custom themes] [Playground]

Mode           Light   Dark   System
Preset family  [mint] [themvora] [citrus] [cocoa] [berry] …

[Toggle light / dark]

┌─ Theme controls ────────────────┐
│ live preview · swatches · tokens │
└──────────────────────────────────┘

┌─ Scoped to cocoa ───────────────┐
│ a subtree pinned to one family   │
└───────────────────────────────────┘
```

Every colour comes from a semantic token. The generated stylesheet contains no
literal colour, and the generated components contain none either — which is what
makes a theme switch visibly real, and what makes the showcase a correct
reference for the semantic system rather than a decorative demo.

The showcase UI is its own component rather than living in the application root,
and there is exactly one provider boundary:

```text
src/
├── main.tsx                     mounts the app; the provider boundary lives here
├── App.tsx                      composes the showcase
├── index.css                    the generated stylesheet
├── components/
│   ├── ThemvoraDefault.tsx      the showcase UI
│   └── ThemeSwitcher.tsx        the light/dark control
└── themes/
    └── themes.ts                the theme module
```

Each framework uses its own conventions for the same split:

| Framework | Provider | Application root | Showcase | Theme module | Stylesheet |
| --------- | -------- | ----------------- | -------- | ------------ | ---------- |
| React | `src/main.tsx` | `src/App.tsx` | `src/components/` | `src/themes/themes.ts` | `src/index.css` |
| Next.js | `app/layout.tsx` | `app/page.tsx` | `components/` | `themes/themes.ts` | `app/globals.css` |
| Vue | `src/App.vue` | `src/App.vue` | `src/components/` | `src/themes/themes.ts` | `src/style.css` |
| Svelte | `src/App.svelte` | `src/App.svelte` | `src/components/` | `src/themes/themes.ts` | `src/app.css` |
| Solid | `src/App.tsx` | `src/App.tsx` | `src/components/` | `src/themes/themes.ts` | `src/index.css` |

The app opens in a **light** theme. The provider receives `initialMode="light"`
and the source's light theme by name, so a first run looks the same for every
visitor instead of following the operating system. A selection the user has
already made still wins, as the runtime's persistence contract requires.

### The theme module

`themes/themes.ts` is the one file that names colours, and it is generated from
canonical core APIs rather than copied from a template. It exports:

| Export | What it is |
| ------ | ---------- |
| `themvora` | the custom `themvora` light/dark pair |
| `selection` | the families the app offers — the source's own, plus the four demo families |
| `presetThemes` | `getPresetThemes()` filtered by `selection` — the canonical presets, referenced rather than copied |
| `sourceThemes` | themes the catalog cannot serve (a brand, a seed, the neutral pair), written out |
| `themes` | everything the application registers |
| `defaultTheme` | the theme the app opens with, typed against the registry's own names |
| `scopedFamily` / `scopedThemes` | the family the scoped demo pins to, resolved from the registry rather than hardcoded |

The `shadows` group is deliberately absent from the custom pair: shadow tokens
are CSS box-shadow values, so a bare colour would emit an unusable
`--theme-shadow-sm`. Empty optional groups are omitted for the same reason.

### `--example`

The showcase is the starter. There is no minimal variant to opt out of, so
`--example` changes nothing about what is written. The flag is still accepted so
that scripts written against an earlier release keep working.

## Styling

```bash
themvora init my-app --framework react                     # plain CSS — the default
themvora init my-app --framework react --styling css       # plain CSS, explicitly
themvora init my-app --framework react --styling tailwind  # Tailwind CSS
```

`--styling` chooses how the generated application is styled, and it defaults to
plain CSS — in the wizard and outside it. In a terminal the wizard asks the same
question — *Would you like to use Tailwind CSS with Themvora?* — with **No —
Plain CSS** preselected. Pressing Enter and running `themvora init` with no
terminal both produce the same project. Passing the flag skips the question
entirely.

Plain CSS is the default because it is the only choice that adds no build-time
dependency: a project that a script generates, or that someone accepts without
thinking about it, should not acquire a CSS framework it never asked for.
Tailwind is one answer away, at the prompt or with `--styling tailwind`.

**`tailwind`** writes a Tailwind CSS v4 entry point that imports `tailwindcss`
and then `@themvora/tailwind`, whose `@theme` mapping turns Themvora's tokens
into utilities — `bg-background`, `text-foreground`, `bg-card`, `border-border`,
`bg-primary`. It adds `@themvora/tailwind` to the dependencies, and
`tailwindcss` plus the framework's own plugin (`@tailwindcss/vite`, or
`@tailwindcss/postcss` for Next.js) to `devDependencies`, and registers the
plugin in the build configuration.

**`css`** writes one global stylesheet that reads the same tokens through
`var(--theme-color-background)`, `var(--theme-color-card)`,
`var(--theme-color-primary)` and friends. It adds no dependency at all, and no
build configuration — there is nothing to compile.

Either way the showcase contains **one** styling system: no `:root` palette, no
`prefers-color-scheme` block, no literal colour in a component. Switching themes
repaints the whole showcase in both, including the page itself — the document
background and text come from the theme, not from the browser default.

The two variants do not produce the same markup with a different stylesheet
bolted on. The `css` variant renders component classes (`class="card"`) that the
generated stylesheet defines from semantic variables. The `tailwind` variant
renders Tailwind utilities (`class="grid gap-4 rounded-xl border border-border
bg-card p-6"`) and defines **no** component classes at all — its stylesheet is
the Tailwind entry point plus a body rule.

What they do share is everything that makes the app an app: the same page, the
same cards and controls, the same theme switcher, the same responsive
breakpoints, the same tokens. Choosing plain CSS is a choice about how the
stylesheet is written, not a downgrade to an unstyled page.

`--styling` is deliberately not called `--style`: `--style` already means a theme
*generation* style (`themvora generate --style minimal`), which is a different
concern. And there is no `--tailwind`/`--no-tailwind` pair — two flags for one
setting is how a CLI ends up with two ways to say the same thing and no way to
say which won.

### Styling an existing project

`--styling` is a choice about a project `init` is about to create. In an
existing project it can only reach the files `init` generated: a stylesheet you
wrote yourself is a conflict, not a target, so the run tells you which of the two
it found instead of quietly restyling your app.

```text
! --styling tailwind only rewrites the stylesheets `init` generated — a
  stylesheet you wrote yourself is left alone unless you pass --force
```

If you do want the matching rules in a project you already have, pass `--force`
to replace its root stylesheet, or copy them across yourself.

## A fresh project versus an existing one

The two workflows are deliberately different.

For a project `init` scaffolded, the CLI owns the generated structure. It writes
the showcase, and it **removes the scaffold's own unused files** — the demo
stylesheet that declares a second palette, the demo component, the logo assets
the generated UI never renders. A file is removed only when it is a known
artifact of that framework's template *and* nothing left in the project refers to
it, so a dangling import is never produced.

For an existing project, none of that happens. The CLI adds its own files and
reports anything it cannot do safely as a manual step with the exact snippet.
Your `App`, your stylesheets and your build configuration are left alone —
including any Tailwind setup you already have. Nothing registers a Themvora
plugin in your build: initialization is provider props.

## The plan and dry run

```bash
themvora init my-app --framework react --plan
themvora init my-app --framework react --dry-run
```

Both are built from the **same plan object** a real run applies, so the preview
cannot drift from the outcome. Neither writes a file, installs a package or
invokes a scaffold — `--dry-run` never runs an external generator.

For a new project the preview is computed before the generator has run, so the
files Themvora owns are exact while the edits to the generator's own files are
resolved afterwards. The plan says so.

## What is wired

Initialization is **provider props**. There is no configuration file and no build
plugin:

```text
themes/themes.ts
        ↓
<ThemeProvider themes={themes} defaultTheme={...} initialMode="light" transition={...}>
        ↓
pre-paint bootstrap
```

One module, one consumer. The provider paints `<html>` before the first paint —
its own contract, so a client-rendered app needs neither `themvoraVitePlugin()`
nor a hand-rolled pre-paint script. React uses the same path; `createThemeRoot`
remains the documented entry for server rendering.

Next.js follows the same shape. `@themvora/next`'s `ThemeProvider` renders
`<html>` and `<body>` itself and resolves the initial theme on the server, so
there is no Vite plugin either, and the registry is passed to the provider as a
prop. Client hooks come from `@themvora/next/client`, never from the package
root.

### Next.js 16 and Cache Components

`create-next-app` now enables **Cache Components** by default, and the generated
layout needs **nothing extra** — in particular no `export const instant = false`.

That mode rejects a route that reads request data (`cookies()`, `headers()`)
outside a `<Suspense>` boundary, and Next's remedy for such a route is the
`instant = false` opt-out. `@themvora/next`'s provider keeps that read *inside* a
boundary instead: the `<html>`/`<head>`/`<body>` shell resolves from the
configured default alone, and the persisted selection is resolved in a nested
server component beneath `<Suspense>`. The route therefore prerenders as a static
shell with a dynamic, request-aware hole, so there is nothing to opt out of.

The visitor's theme still reaches the first paint through two mechanisms that
agree with each other: the blocking bootstrap script in `<head>` reads the theme
cookies in the browser and writes the resolved theme onto `<html>` before the
first frame, and the Suspense-gated server component resolves the same cookies
for the client runtime and the streamed, server-rendered subtree.

`init` leaves your `next.config.ts` alone either way.

## Exit codes

| Code | Meaning |
| ---- | ------- |
| `0` | The project was created or integrated, and verified |
| `3` | The project was written, but a verification step failed |
| `1` | Command or runtime error, or existing files block the run |
| `2` | Usage or argument error |
| `130` | The interactive wizard was cancelled (Ctrl+C); nothing was written |

A verification failure exits `3` rather than `0` deliberately: `init` claims to
produce a *working* application, so a project that does not build is not a
success. A cancellation exits `130` — `128 + SIGINT`, the conventional shell
value — so a wrapper script can tell "the user changed their mind" from "the
command failed".

## Safety

`init` modifies your project, so the guarantees are explicit:

- Nothing is derived from an untrusted value into a command. The one piece of
  user input that reaches a child process — the scaffolded directory name — is
  validated against a conservative character set first.
- Every generated path is resolved and checked against the project root, so no
  registry value or theme name can write outside the project.
- Commands are passed as argument arrays. A shell is used only on Windows, where
  the package managers are `.cmd` shims that cannot be launched otherwise.
- The exact command being run is printed before it runs.
- No remote template repository is ever downloaded by Themvora's own logic;
  scaffolding is delegated to the ecosystem's official generator.
