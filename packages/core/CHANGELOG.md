# @themvora/core

## 1.6.0

### Minor Changes

- Make the Web Components first paint correct without a manually authored
  bootstrap script.

  `themvoraVitePlugin()` now emits, from the discovered `theme.config.ts`:

  - a render-blocking `<style>` generated by `createThemePrePaintCss()` — the
    fallback theme under `:root`, a `prefers-color-scheme: dark` fallback for
    `initialMode: "system"`, and one `:root[data-theme="…"]` rule per declared
    theme;
  - the serialized configuration global;
  - the existing classic blocking boot script.

  The resources are injected in that order in development and production, so the
  CSS is applied before the script runs. The plugin also validates the provider's
  `themes`, `default-theme` and `initial-mode` against the config and fails the
  build when they resolve differently. Provider JSON theme definitions are
  included in the generated CSS.

  The pre-paint readout contract now accepts `data-tv-readout="effective-mode"`:
  the applied light/dark, as distinct from `"mode"` (the visitor's selection,
  which may be `system`). This lets a static readout show both before the runtime
  mounts.

  New public surface:

  - `createThemePrePaintCss(options)` in `@themvora/core`;
  - `applyThemeBootstrap(plan, options)` in `@themvora/core` — the DOM applier the
    static boot asset and the generated script share;
  - `@themvora/web/boot.js`, a static classic boot asset for non-Vite pages;
  - `@themvora/web/vite`, a re-export of the same Vite plugin from the package a
    Web Components app already installs.

  New diagnostics:

  - `TV_PREPAINT_MISSING` — the runtime started after a paint with no pre-paint
    setup;
  - `TV_PREPAINT_MISMATCH` — the painted theme is not in the registry or differs
    from the resolved theme.

  Both are one-shot warnings through the existing diagnostic pipeline. The manual
  `createThemeBootstrapScript()` path is unchanged. `examples/apps/web` is
  replaced with a Vite vanilla-TS first-paint reference, and the framework guide
  and compatibility matrix now classify Web Components zero-flash as automatic
  with the verified Vite plugin.

### Patch Changes

- Fix the first-frame scroll flash on Astro hard loads, and make the
  serializable `transition` / `scrollbar` configuration usable.

  `<ClientRouter />` sets `history.scrollRestoration = "manual"` and restores the
  position it saved in `history.state` from its **deferred module**. On a slow
  load — and in dev, where the module graph is larger — that module runs after the
  document has painted, so a reload paints the top of the page and jumps to the
  saved position afterwards. `provider.astro` now restores the same Astro-managed
  position from an inline script at the end of `<body>`, before the router module
  and before the first paint. It reads `history.state` (no `sessionStorage` key),
  leaves native restoration and the router's ownership of client-side navigation
  and back/forward untouched, and is a no-op without Astro-managed state, so
  ordinary navigation is never handed another entry's position.

  `ThemvoraConfig.transition` and `.scrollbar` were typed `unknown`, so
  `theme.config.ts` offered no completions and no checking for them. They are now
  `boolean | ThemeTransitionOptions` and `boolean | PrePaintScrollbarOptions`, and
  the same fields exist on `ThemvoraThemeConfig`.

  A configured `transition.duration` / `easing` now also applies to the native
  View Transition crossfade; previously that path silently used the UA's fixed
  default, so every configured duration looked identical.

  `ThemeProviderClient` now adopts the transported `transition` too. It previously
  read only its own prop, so an Astro + React page whose `theme.config.ts`
  declared a transition created its island runtime without one (or with the
  defaults) while native controls on the same page used the declaration. An
  explicit prop still wins, so a per-island override keeps working.

## 1.5.0

### Minor Changes

- Built-in themes now reach 4.5:1 text contrast in the cases that previously shipped short of it, which
  changes some preset token values.

  The readability pass over the built-in themes already picked the most readable ink available for each
  surface. What it did not do was act when the _best_ candidate still fell short of 4.5:1 — the theme
  shipped and the text was hard to read. It now takes the remaining step: when no foreground candidate
  reaches the target, the background is moved in sRGB, away from the foreground, until the pair reaches
  4.5:1. It gives up after 50 steps rather than looping on an unreachable target.

  The consequence is visible: **some built-in preset backgrounds are a slightly different hex value than
  in 1.4.0.** No API changed and no token name moved, but a snapshot of a preset's `colors.background`
  taken against 1.4.0 will differ. The theme-generation baselines were regenerated to match, so
  `scoreTheme()` and `validateThemeContrast()` agree with what ships.

  If you diff rendered output against a pinned 1.4.0 fixture, expect the difference; if you were relying
  on a preset's exact background hex, read it from the theme rather than hardcoding it.

  `@themvora/web` moves with `@themvora/core` as a fixed release group and gains the symbols through its
  re-export.

- Add `hideNativeScrollbar()` / `restoreNativeScrollbar()` and the stylesheet identifiers they use.

  Overlay scrollbars need the platform's own bars gone, and until now each integration did that with its
  own injected `<style>` — which meant two of them on one page fought over the same rule, and a
  server-rendered page could not tell whether the client had already installed it.

  ```ts
  import { hideNativeScrollbar, restoreNativeScrollbar } from "@themvora/core";

  const restore = hideNativeScrollbar();
  // … later, on teardown
  restore();
  ```

  `hideNativeScrollbar()` is claim-based and returns the release function for its claim. The marker class
  and the stylesheet are installed idempotently — a server-rendered class or an identical SSR stylesheet
  is reused rather than duplicated — and the native bar stays hidden until the _last_ claim is released.
  That is what makes it safe for two independently mounted scrollbars on one page: the first to unmount
  does not restore the bar under the second.

  `restoreNativeScrollbar()` is the unconditional teardown, for a path that wants the native bar back
  regardless of outstanding claims.

  `SCROLLBAR_HIDING_STYLE_ID` and `SCROLLBAR_HIDING_STYLE_ATTR` are exported so a server-rendered
  document and the client agree on which element to look for rather than each guessing at an id.

  `@themvora/web` moves with `@themvora/core` as a fixed release group and gains the symbols through its
  re-export.

- Add the provided-themes surface and a one-shot `themeOverride`, so a provider can report what it was
  actually given and a caller can outrank a saved selection.

  Until now the runtime could only tell you the _selected_ theme. A provider that supplies three families
  and a caller that wants "dark, but this page is the checkout" had no way to say either thing without
  mutating persistence.

  ```ts
  import {
    createThemeRuntime,
    createProvidedThemesSource,
  } from "@themvora/core";

  const runtime = createThemeRuntime({
    themes,
    // Applied once per value, and never written to storage.
    themeOverride: { family: "checkout", mode: "dark" },
  });

  const provided = createProvidedThemesSource(runtime);
  provided.get();
  // [{ family: "checkout", variants: [{ name: "checkout-dark", mode: "dark", tokens, theme }, …],
  //    provenance: { kind: "pack", pack: "acme" } }, …]
  ```

  - `createProvidedThemesSource(runtime)` returns `{ get(), subscribe() }` — a stable snapshot plus a
    subscription, so it can back `useSyncExternalStore` directly. `get()` returns the same array instance
    until the provider's theme list actually changes, and a re-registered catalog whose only difference
    is the registry's `meta.created` / `meta.updated` stamps is not treated as a change.
  - `normalizeProvidedThemes(themes)` is the same grouping without the reactivity, for callers that
    already have a settled array.
  - Families are grouped in the order the provider supplied them, and each variant carries its resolved
    tokens — `auto()` / `contrast()` / expressions already evaluated — plus the original definition for
    anything the grouped view does not model.
  - `ProvidedThemeProvenance` is declared, never inferred: `{ kind: "generated", algorithm }` from
    `meta.generation`, `{ kind: "pack", pack }` from a `pack:<name>` tag. A theme called `mint-light` is
    not thereby a preset.
  - `resolveThemeReference(themes, "cocoa-dark")` resolves a name against a theme list and reports what
    it matched; `resolveThemeOverride()` and `themeOverrideKey()` make the override idempotent — the
    runtime applies an override once per _value_, so re-rendering with a freshly allocated object does
    not re-apply it, and an override never reaches storage.

  `ThemeRuntimeOptions.defaultTheme` and `initialFamily` now accept `ThemeIdentifier<T>` rather than a
  family name. This is a **widening**: every value that typechecked against 1.4.0 still typechecks, and
  you can additionally pass a variant name where a family was expected. A variant supplies its own mode
  unless `initialMode` is given, so the two options cannot silently disagree.

  `@themvora/web` moves with `@themvora/core` as a fixed release group and gains the symbols through its
  re-export.

- Add `loadThemeRegistry()`, a static reader for the theme registry `themvora init` generates.

  `themvora init` writes `src/themes/themes.ts` (or `themes/themes.ts` for Next) and, for React, Vue,
  Solid and Svelte, no `theme.config.ts` at all. That module is the canonical theme registry, and until
  now no consumer could read it without executing workspace TypeScript — which is arbitrary code
  execution, and something an editor or CI step should never require to show a colour. The result was
  that every canonically initialized project was unreadable to any tool other than the app itself.

  The loader reads the module **as data**:

  ```ts
  import { loadThemeRegistry } from "@themvora/core";

  const result = loadThemeRegistry(source);
  if (result.ok) {
    result.themes; // every theme the module registers, in its own order
    result.origins; // "definition" | "catalog", aligned with themes
    result.selection; // the families it selects
    result.defaultTheme;
  } else {
    result.reason; // "not-a-registry" | "unsupported-construct" | "invalid-theme"
    result.message; // a sentence, with a line and column where one is known
  }
  ```

  It parses the `defineTheme({ … })` literals, reads the `selection` string array, resolves
  `presetThemes` through `getPresetThemes()` exactly as the module would at runtime, and validates every
  theme with `validateTheme()`. It does not import, transpile, evaluate or interpret expressions: a
  computed argument, a spread, or a non-literal `selection` is reported as `unsupported-construct` rather
  than guessed at.

  `origins` is the per-theme provenance the combined list cannot carry: a generated registry mixes the
  application's own definitions with the preset families in `selection`, and a consumer that needs to
  count or label project themes must not count those presets as project-defined.

  The point of putting this in `core` rather than in a consumer is that the interpretation is shared —
  the VS Code extension uses it today, and the CLI, documentation tooling and future editors can use the
  same one instead of each growing their own.

  `@themvora/web` moves with `@themvora/core` because they are a fixed release group; it re-exports core
  and gains the symbol with no code change of its own.

- Add `readThemeDefinitions()`, a static reader for `defineTheme()` definitions in any source file.

  `defineTheme()` returns its argument unchanged — it is a type-level helper, not a transformation — so a
  readable object literal _is_ the theme. That is what makes a static reader sufficient: there are no
  defaults to apply, no variants to resolve and no metadata to derive.

  ```ts
  import { readThemeDefinitions } from "@themvora/core";

  const { definitions, problems } = readThemeDefinitions(source);
  // definitions: [{ theme, location: { line, column }, binding?, variant?, generateOptions? }, …]
  // problems:    [{ message, location }, …]
  ```

  Each definition also reports the declaration it is assigned to (`binding`) and, for a generated pair,
  which half it is (`variant`) — `export const { light: lightTheme } = generateTheme(…)` reports
  `lightTheme` / `"light"`. That lets a consumer follow an exported symbol into another module without
  re-parsing the declaration itself. Both fields are optional; a literal inside an array has no single
  name standing for it and reports neither.

  Each definition also reports the canonical API that produced it (`origin`: `"definition"`,
  `"generated"` or `"catalog"`), so a consumer can distinguish an application's own theme from a
  curated preset without maintaining its own catalog list.

  For a generated pair, the literal options passed to `generateTheme()` are reported as
  `generateOptions` (`seed`, and any of `family`, `style`, `contrast`, `algorithm`, `withCode` that the
  call supplied). This is the data the call was given, not an evaluation of it: an identifier, call or
  spread argument is still refused. A tool can therefore show the inputs that produced a source theme
  rather than only its resulting tokens.

  `readThemeDefinitions(source, options)` now also accepts `strict`, `bindings` and `namespaces`. In
  strict mode there are no name defaults: `defineTheme`, `generateTheme` and the catalog functions are
  canonical only when a verified import binding (or a namespace member from a verified package) says
  so. A local function called `getPresetThemes` is then not the catalog. The extension uses strict
  mode with the exports of `@themvora/core`, `@themvora/core/vanilla` and the Nuxt core re-export;
  standalone callers that omit the options keep the spelling-based defaults. A namespace member call
  resolves through the documented `{ local: "*" }` binding (or a `namespaces` entry in strict mode).

  Broader than `loadThemeRegistry()`, which requires the canonical registry's `themvora` / `selection` /
  `sourceThemes` exports. This finds definitions anywhere — a project may keep them in `src/theme/brand.ts`
  — and returns the candidates it could not read instead of dropping them, so a caller can say why.

  It does not evaluate anything: a spread, a call, a template with interpolation or an identifier argument
  is reported as a problem, never executed. A `defineTheme(...)` inside a comment or a string is ignored,
  because that is documentation rather than a definition.

  The VS Code extension uses it to show themes defined outside the generated registry. `@themvora/web`
  moves with `@themvora/core` as a fixed release group and gains the symbol through its re-export.

- Add `parseThemeJson()` and `themeToCssDocument()`, so a theme can be read from JSON and written back
  out as CSS without reimplementing either step.

  Both exist because the same two jobs kept being written by hand in different places — the CLI reading a
  `theme.json`, a build step emitting a stylesheet — and each copy drifted on the details that matter.

  ```ts
  import { parseThemeJson, themeToCssDocument } from "@themvora/core";

  const { value, source } = parseThemeJson(text);

  // A hand-maintained theme.json is JSONC in practice: comments and trailing commas.
  // `source` is the same length as `text`, with those regions blanked to spaces, so
  // any offset you report from a parse error still points at the right character.
  themeToCssDocument({ light, dark });
  // ":root { --theme-color-background: …; }\n\n[data-theme=\"dark\"] { … }"
  ```

  `themeToCssDocument()` accepts a single definition or a `{ light, dark }` pair and emits one block per
  mode against `CSS_ROOT_SELECTOR` / `CSS_DARK_SELECTOR`, both now exported so a consumer writing its own
  stylesheet does not hardcode `:root` and `[data-theme="dark"]` and then fall out of step when the
  runtime's selector changes.

  `@themvora/web` moves with `@themvora/core` as a fixed release group and gains the symbols through its
  re-export.

## 1.4.0

### Minor Changes

- Add `computeFingerprint` to `@theme-kit/core`.

  The fingerprint is the cache-busting half of the zero-flash cookie contract
  (`theme-mode` / `theme-family` / `theme-fingerprint`): it is written on every
  SSR response and compared on the next request, so a stale value invalidates a
  persisted selection after the theme registry changes. Because it is part of that
  contract, it has to be **byte-identical** across every SSR integration.

  It was not. Astro, Next, Nuxt and Remix each carried a private, byte-identical
  copy. Nothing compared them, so editing one would have silently broken
  cross-framework persistence — a visitor's saved theme would stop being honoured
  in exactly one framework, with no error anywhere.

  The implementation now lives in core and the four integrations re-export it.
  This is an **additive** change: the format and the emitted values are unchanged
  (verified against the pre-refactor output for all four integrations, including
  the built HTML), so no persisted selection is invalidated. `@theme-kit/astro`
  and `@theme-kit/nuxt` still export `computeFingerprint` from their public entry
  with the same signature; Next and Remix keep it internal, as before.

- Make core's `createDevToolsPlugin` entry conform to the documented devtools contract.

  There are two public functions named `createDevToolsPlugin` — core's lightweight
  bridge, and the inspector in `@theme-kit/devtools`. Both register their entry on
  the same `window.__THEME_KIT_DEVTOOLS__` set, and the docs declare that set's
  member shape as:

  ```ts
  Set<{
    getState(): unknown;
    getEntries(): unknown[];
    getPerformance(): unknown[];
  }>;
  ```

  Core's entry only had `getState()`. So the consumer loop the docs actually show —
  `for (const inspector of window.__THEME_KIT_DEVTOOLS__ ?? []) inspector.getEntries()` —
  threw `TypeError: inspector.getEntries is not a function` on any page that
  installed core's plugin rather than the inspector one. Verified by running that
  exact loop against the pre-fix entry shape.

  Core's plugin records no entries and no performance samples, so the two added
  methods return empty arrays; the point is that every member of the set is now
  callable through the declared interface without a type check. With both plugins
  installed on one runtime, both entries now conform (verified).

  No declared type changed and no export was added or removed, so this is
  source-compatible. The runtime behaviour of the entry is unchanged apart from
  the two new methods.

- Resolve the pre-paint script's fallback mode from the same source as the client
  runtime, so the two cannot disagree.

  `buildBootstrapPlan` hardcoded `fallbackMode = initialMode ?? "system"`, while
  `resolveInitialTheme` defaults `mode` to the fallback theme's own mode. For any
  caller that omitted the mode the two therefore resolved _different_ themes: on
  an OS-dark machine the script painted the dark theme and the runtime corrected
  it to light — a measured flash of up to ~1.5 s on the shipped examples.

  The script's fallback is now derived from `resolveInitialTheme` itself, which is
  exactly the value the runtime adopts from its own call. `"system"` is now opt-in
  rather than the silent default, and reaching it requires saying so to both
  halves (`themeKitVitePlugin({ initialMode })` and the provider's `initialMode`).

  Also in this release:

  - Add `systemModeCSSTemplate(light, dark)` — the CSS-only resolution of a
    `"system"` selection. Emits one `prefers-color-scheme` block per scheme and
    expects no inline variables. See the note below for why the existing
    `darkModeCSSTemplate` cannot be combined with a server-rendered inline `style`.
  - `createThemeRuntime()` no longer requires an argument. Every other factory in
    the package defaults its options to `{}`; this one threw, so
    `createThemeRuntime()` — the form the docs show — failed at runtime.
  - A falsy `family` (`""`, which a cookie or a DOM attribute can produce) is
    normalised to the fallback's family. Previously `""` survived into the
    selection and every lookup degraded to `themes[0]`, so a `dark` selection
    silently resolved to the _light_ theme.
  - `resolveSelectedTheme` now falls back to a theme of the requested mode before
    giving up on the mode entirely.

  **Behaviour change, please read.** A `"system"` selection can no longer be
  expressed by inlining the resolved variables plus a dark media block: an inline
  `style` on `<html>` outranks every stylesheet rule, so the dark block never
  applies and an OS-dark visitor keeps the light colors. Measured on a production
  build with scripts blocked, that combination painted `rgb(248, 250, 252)`; the
  same variables emitted as a `<style>` element with both schemes painted
  `rgb(2, 6, 23)`. `systemModeCSSTemplate` is the supported way to do this. Only
  `"system"` may use media queries — a concrete mode must be a plain `:root` rule,
  or it would follow the OS when the script is blocked.

  Web: `theme-kit-provider` gains `initial-mode` and `initial-family` attributes.
  The custom element previously could not express a mode at all, so
  `initialMode` was unreachable from HTML.

### Patch Changes

- Keep `data-theme-selection-mode` / `data-theme-selection-family` in sync with
  the live selection.

  The pre-paint bootstrap and the SSR layouts publish the visitor's _selection_
  under those two attributes, and nothing maintained them afterwards. After the
  first client-side change the document advertised the selection the page had
  loaded with: pick `system`, then `dark`, and `<html>` still said
  `data-theme-selection-mode="system"` — for the rest of the session, on every
  framework.

  The resolved attributes cannot stand in for them. `data-theme-mode` and
  `data-theme` describe the theme that was _applied_, and a `"system"` selection is
  resolved to `"light"`/`"dark"` before either is written, so the choice is
  unrecoverable from them. Anything reading the selection — CSS,
  `readBootstrapState`, a framework-free control — was reading the state of the
  page as it was loaded.

  `createDOMBinding` now takes an optional `selection` source and mirrors it onto
  both attributes, in the same write batch as the resolved attributes so the two
  can never be observed disagreeing. It subscribes to the selection _as well as_
  the store: a selection change that resolves to the same theme
  (`setMode("light")` while the OS preference is already light) emits no store
  change, so a store-only binding would never run. `createThemeRuntime` and
  `ThemeKit` pass their selection controller in; a binding created without one
  writes neither attribute, exactly as before.

  Verified in the browser: after `setMode("dark")` the attribute reads `dark`, and
  it survives a reload. All 436 core tests pass.

- Never let the selection name a theme family that is not in the registry.

  A family is an invariant, not free-form text. `resolveThemeName` filters the
  registry by family and falls back to `themes[0]` when nothing matches, so a
  selection carrying an unregistered family resolves to the _first_ theme — while
  `data-theme-selection-family` (and every `data-tk-readout="family"`) keeps
  naming the family that is not on screen. The readout then contradicts
  `data-theme-family` / `data-theme`, and the browser disagrees with the server,
  which is a visible correction on load. On the Astro example with an `oat`
  family selected, the readout alternated between the applied family and a stale
  one across reloads.

  A persisted family is the usual source: a cookie or `localStorage` entry
  written before the application changed its family set. Nothing validated it,
  because a family that was once registered and has since been removed is
  indistinguishable from one that never existed.

  Three paths in `@theme-kit/core` now normalise through a single `@internal`
  `normalizeThemeFamily` helper (built on `getThemeFamilies`), which returns a
  registered family or the fallback theme's own family:

  - `resolveSelection` — the SSR/server path, for a persisted selection and for
    `initialFamily` alike. `??` only catches `null`/`undefined`, so an
    `initialFamily` of `""` (what some cookie readers yield for a missing cookie)
    previously survived into the selection too.
  - `createThemeSelectionController`'s initial state, so the client starts from a
    family the registry actually has.
  - The inline pre-paint script. `ThemeBootstrapPlan` gains a `families` list
    taken from the same registry the CSS map was built from, and the generated
    script rejects a persisted family that is not in it. The two are therefore
    either both present or both absent, so the script can never accept a family
    the map has no variables for.

  **Behaviour change, please read.** `setFamily()` now ignores a family the
  registry does not have, instead of applying it and degrading to `themes[0]`. A
  caller that passes an unregistered family has a bug; a no-op keeps the
  selection honest and the readout shows it, whereas switching the visitor to a
  _different_ family than the one requested would hide it.

  Astro is the only framework that hand-assembles its bootstrap plan, so it now
  threads `families` through `buildThemeBootstrapPayload` →
  `createBlockingScript` → `integration.ts` / `provider.astro`. Every other
  framework calls the shared serializer and inherits the guard; `@theme-kit/web`
  does too.

  Verified: 449 core tests pass, including 13 new in
  `family-normalization.test.ts`. The Astro readout regression gate runs 12/12,
  and its stale-family row was confirmed by fault injection — restoring the
  unguarded selection fails the gate with
  `readout family="mint" disagrees with data-theme-family="oat"`.

## 1.0.0

### Major Changes

- Release Theme Kit 1.0.0 — the first stable release of the framework-agnostic
  theming runtime. Semantic tokens, theme families, SSR-safe hydration with zero
  flash, smooth transitions, scoped themes, persistence and history,
  multi-window sync, scheduling, a custom scrollbar, a CLI, and adapters for
  React, Next.js, Vue, Nuxt, Svelte, Solid, Angular, Astro, Remix, Tailwind, and
  the major UI libraries (shadcn/ui, Bootstrap, daisyUI, Open Props, Material UI,
  Chakra UI, Ant Design, Mantine, UnoCSS).

### Minor Changes

- `generateTheme` now produces modern, branded, accessible themes. `primaryForeground` is derived from the seed's WCAG relative luminance instead of being hardcoded white, so light/brand colors get a near-black ink (`#f59e0b` → `#0f172a`) instead of unreadable white-on-amber text. Both light and dark modes emit the complete semantic palette (`background`, `foreground`, `card`, `popover`, `secondary`, `muted`, `accent`, `destructive`, `success`, `border`, `input`, `ring` + their foregrounds) plus `radius.lg`, and `meta.order` (10/20) so generated themes slot into preset ordering. Neutrals are tinted from the seed hue, so every generated family feels cohesive and branded. The CLI `generate` command and the `/theme-studio` + playground generators pick this up automatically.

### Patch Changes

- Add a `require` condition to the `exports` map so CommonJS consumers (such as
  the `@theme-kit/cli` CJS binary) can resolve `@theme-kit/core`,
  `@theme-kit/core/vanilla`, and `@theme-kit/core/vite` (`ERR_PACKAGE_PATH_NOT_EXPORTED`
  previously). Also emit `success` and `successForeground` color tokens in
  `generateTheme` (light + dark), so generated themes satisfy the validator's
  required color set and pass `theme-kit validate` out of the box.
